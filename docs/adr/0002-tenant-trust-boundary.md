# ADR 0002 · 共享库中的租户信任边界

2026-11-11 · Day 7

## 决策

当前使用共享 MySQL 库、共享表。服务端在每次企业请求中以已验证的 GVA JWT 识别账号，以实时查询到的活跃成员关系建立租户上下文。数据库通过带租户条件的查询和复合外键约束数据访问与关联。

```mermaid
flowchart LR
    A["浏览器发送 JWT 与 X-Tenant-ID"] --> B["JWTAuth 验证令牌并提取账号"]
    B --> C["企业路由拒绝平台账号"]
    C --> D["按账号与所选租户查询有效成员关系"]
    D --> E["服务端生成 TenantContext"]
    E --> F["Casbin 校验租户域、角色和动作"]
    F --> G["部门查询同时限制 tenant_id 与 id"]
```

| 输入 | 使用方式 |
| --- | --- |
| JWT | 验证后取账号 ID。角色和成员状态以数据库查询为准。 |
| `X-Tenant-ID` | 作为租户选择候选。缺失、重复或格式非法被拒绝。 |
| URL 部门 ID | 作为资源定位条件，与可信租户 ID 一并进入仓储条件。 |
| 改名请求体 | 只接收部门名称。额外字段被拒绝。 |
| 成员关系 | 同时校验账号、租户和成员状态，使用成员所在租户及其角色。 |

工作台发现接口仅使用 JWT 账号查询活跃成员关系。平台接口走独立授权路径，用配置的运营账号 UUID 和实时账号状态校验，提供租户元数据。菜单控制显示可用操作，后端在处理动作时再次执行授权。前端切换租户时清理旧权限与详情，取消旧读取并过滤迟到响应。

## 影响

共享表便于统一迁移和本地复现。每个企业仓储入口都需要显式检查租户上下文，复合外键用于约束关联。例如成员的部门归属必须匹配 `(tenant_id, department_id)`。独立数据库能将误查询限制在单租户数据库内，同时需要维护租户连接路由、迁移和备份。

关键失败边界是合法账号持有 A 的角色，但请求中选择 B 或传入 B 的部门 ID。前者依赖实时成员检查，后者依赖查询的租户条件。已开始的请求使用本次检查获得的上下文，成员停用后的回归覆盖下一次请求。
