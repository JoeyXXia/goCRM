# Day 2 数据库迁移与测试环境

日期为 2026-11-08（Asia/Shanghai）。起点是 Day 1 提交 `2b6b0818`。本机验证使用 Windows、Go 1.26.5、Node 22.14.0、npm 10.9.0 和 MySQL 8.0.44。

## 三个审查单元

1. **测试数据库与迁移**。测试 Compose 只包含 MySQL，绑定本机端口 13307，使用临时数据目录。健康检查用测试账号对目标库执行 `SELECT 1`。迁移命令复用现有驱动，先校验 DSN 库名，再在同一连接上核对实际库名并获取锁。首个 SQL 建立 `crm_schema_migrations`，验证表结构后登记版本和 SHA-256 校验和。SQL 固定 LF，确保不同检出环境使用相同校验和。 [测试 Compose](../../deploy/docker-compose/day2-test.yaml) · [迁移命令](../../server/cmd/dealflow-migrate/main.go)
2. **后端验证**。真实 MySQL 测试核对迁移复跑、校验和及夹具事务回滚。Gin 路由测试调用实际注册的 `POST /init/checkdb` 并检查返回契约。浏览器回归使用 Day 1 已初始化的开发库。 [MySQL 测试](../../server/cmd/dealflow-migrate/main_test.go) · [路由测试](../../server/router/system/sys_initdb_test.go)
3. **前端检查与 CI**。固定 TypeScript 5.9.3 为开发依赖，`checkJs` 只检查实际被页面引用的 `stringFun.js`。Day 2 workflow 将后端测试和构建、前端锁文件安装、类型检查和构建放入两个任务。 [类型检查配置](../../web/tsconfig.day2.json) · [CI](../../.github/workflows/day2.yml)

## 复现

PowerShell 从仓库根目录启动专用容器。先在当前终端设置 `DEALFLOW_TEST_MYSQL_PASSWORD` 和 `DEALFLOW_TEST_MYSQL_ROOT_PASSWORD`，再执行下面的命令。

```powershell
docker compose -f deploy/docker-compose/day2-test.yaml up -d --wait --wait-timeout 180
$env:DEALFLOW_TEST_DSN = "dealflow_test:${env:DEALFLOW_TEST_MYSQL_PASSWORD}@tcp(127.0.0.1:13307)/dealflow_crm_test"
Push-Location server
go run -mod=readonly ./cmd/dealflow-migrate
go test -mod=readonly ./cmd/dealflow-migrate ./router/system -count=2
go build -mod=readonly . ./cmd/dealflow-migrate
Pop-Location
docker compose -f deploy/docker-compose/day2-test.yaml down

Push-Location web
npm.cmd ci --no-audit --no-fund
npm.cmd run typecheck
npm.cmd run build
Pop-Location
```

也可将 `DEALFLOW_TEST_DSN` 指向已有 MySQL 8.0.44 的 `dealflow_crm_test`。给测试账号授予该库的 `SELECT`、`INSERT`、`CREATE` 即可复现本次数据库验证。运行 Go 测试时需要设置 DSN，否则集成用例会明确跳过。登录回归按 Day 1 文档启动已初始化的专用开发库和前后端。 [Day 1 启动说明](../day1-setup.md)

## 失败边界

最容易出现的中间状态是 MySQL 已建表，版本登记尚未写入。重跑时迁移命令会检查列、主键和存储引擎，结构匹配才补登记。已登记版本的校验和不符时明确失败。本轮实测了正常重复运行，尚未执行断连故障注入。
