## 实测验收

本地 MySQL 版本为 8.0.44。Day 2 和 Day 3 的数据库与路由测试使用 `-count=2` 连续通过，后端及两个 CLI 的构建通过。迁移命令输出 `Migration 001 verified` 和 `Migration 002 verified`。另用临时账号实跑开通命令一次、种子命令两次，均成功，清理后临时租户及账号合计 0 条。

| 可观察条件 | 本地 MySQL 结果 |
| --- | --- |
| GVA 用户表缺失时阻止 002。准备用户表后可重复迁移 | 首次集成测试确认缺表时三张租户表均未创建。以实际 GVA 模型创建用户表后，连续执行 002 成功。 |
| 同账号在两个企业有独立角色，种子重跑保留相同记录 | 同一账号在 A 为 `sales`、在 B 为 `manager`。重跑前后 8 条成员记录及 ID 一致。对调输入账号后重跑失败，原记录保留。 |
| 数据库拒绝重复成员和跨租户部门 | 同租户重复成员报 MySQL 1062。跨租户部门报外键错误，本地受限账号收到 1216。 |
| 开通时正确关联默认部门和首管理员 | 冻结和软删除的账号被拒绝。启用账号成功绑定 `general` 默认部门及 `tenant_admin` 成员角色。重复租户编码报 MySQL 1062。 |
| 成员写入失败时三张表无残留 | 注入故障前在事务内读到了默认部门。服务返回错误后，通过数据库连接按本次租户 ID 查询，租户、部门和成员记录均为 0。 |

## 复现

按 [Day 2 报告](2026-11-08-day2.md) 准备专用库 `dealflow_crm_test` 和 `DEALFLOW_TEST_DSN`。在项目的 `server` 目录运行。集成测试要求 `demo-a`、`demo-b` 未被占用，并在用户表缺失时通过 GVA 模型建立测试用表结构。测试账号需要在专用库内具备读取、写入、创建表、引用外键和删除夹具的权限。

```sh
go test -mod=readonly ./cmd/dealflow-migrate ./cmd/dealflow-tenant ./router/system -count=2 -v
go build -mod=readonly . ./cmd/dealflow-migrate ./cmd/dealflow-tenant
```

手动操作前，在专用库准备 GVA 用户表和 4 个不同的启用账号。以下 ID 仅作示例，需替换为测试库中的实际账号。

```sh
go run -mod=readonly ./cmd/dealflow-migrate -tenants
go run -mod=readonly ./cmd/dealflow-tenant provision -code example -name "示例企业" -admin 101
go run -mod=readonly ./cmd/dealflow-tenant seed-demo -admin 101 -sales 102 -manager 103 -finance 104
```

## 最容易出错的边界

- GVA 表的主键类型或存储引擎不兼容会中止 002。MySQL DDL 会隐式提交。若迁移在创建表途中失败，修复原因后可重试，迁移仅在结构通过检查后登记。
- 已有种子的默认部门或成员绑定发生变化时，重跑报错并保留现场。跨租户角色目前存放在成员关系中。请求级租户校验和平台权限分组分别属于 Day 4、Day 5。
- 本轮使用本地 MySQL 验收。GitHub Actions、浏览器登录和高并发开通本轮未测。
