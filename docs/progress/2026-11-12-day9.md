# DealFlow CRM · Day 9 数据范围与授权测试

日期 2026-11-12（北京时间）。起点为已推送的 Day 8 提交 `d7d604c2`。

## 当前实现与最小方案

Day 8 已提供可信成员上下文、部门树、成员管理和权限版本。此前成员列表仅允许管理员读取，动作策略没有记录范围。Day 9 在原 Casbin 策略中增加范围字段，将范围解析接入现有成员读取，并提供具有 tenant_id、owner_id、department_id 字段的业务表可复用的查询过滤器。

当前成员读取的默认映射由本轮确定，销售读取本人，财务读取本部门，经理读取本部门及后代，管理员读取本租户全部。管理员可为成员附加销售、财务、经理数据角色，范围按目标动作取并集。详细规则与真值表见 [ADR 0003](../adr/0003-record-visibility.md)。

## 可观察验收

| 条件 | 本地 MySQL 8.0.44 结果 |
| --- | --- |
| 四级范围分别限制本人、本部门、后代和本租户全部 | 参数化用例逐项比较可见记录 ID，并通过签名 JWT 请求成员列表比较可见成员 ID。 |
| 同动作的允许范围取并集，同时保持租户限制 | 销售加财务、销售加财务和经理的并集分别通过。ALL 合并经理范围也通过。异租户同负责人、异租户同部门编号的夹具均未返回。 |
| 业务 OR 条件不能放开权限条件 | 在权限过滤器前后追加恒真 OR 条件，七组矩阵仍只返回预期记录。SELF 可读取本人负责且归属兄弟部门的记录，部门范围不会因此放宽。 |
| 权限修改后旧令牌和旧上下文使用当前版本 | 同一 JWT 下通过 HTTP 更新角色及附加角色后，读取按新范围返回。服务层旧上下文解析得到当前版本。角色集合排序去重后相同的更新保持版本，禁用后旧令牌返回 403。 |
| 范围只能由服务端解析 | 请求体中的 scope 不影响 GET 结果，query 中的 scope 被拒绝。附加数据角色不能授予 tenant_admin。缺失上下文、未知资源与未知动作均被拒绝。 |

首轮矩阵发现 GORM 对单项 OR 及业务 OR 的组合会放宽直接追加的权限条件，随后改为执行期整体分组，并由真实 MySQL 重跑验证。测试账号首次运行缺少临时表权限，在专用测试库内补齐后继续执行。

最终四个 Go 包连续两轮通过，七组矩阵通过 HTTP 更新角色与附加角色后使用同一签名 JWT 验证读取。前后追加 OR 和多行 OR 均保持范围限制。后端及两个 CLI 构建通过，迁移命令确认 001 至 004。Swagger Go 嵌入版与 JSON 的 paths、definitions 一致，YAML 与 JSON 的 DealFlow 路由及成员模型也一致。

演示种子重跑也纳入附加角色漂移校验。已有演示成员被修改数据角色时，种子报错并保留该变化，修复后的完整测试和构建再次通过。

## 复现

沿用独立库 `dealflow_crm_test` 和 `DEALFLOW_TEST_DSN`。测试账号需要此前迁移与 DML 权限，以及 `CREATE TEMPORARY TABLES`。测试记录使用会话临时表，并在返回前删除，业务夹具使用事务回滚。在 `server` 目录执行。

```sh
go test -mod=readonly ./cmd/dealflow-migrate ./cmd/dealflow-tenant ./router/system ./service/tenant -count=2 -v
go build -mod=readonly . ./cmd/dealflow-migrate ./cmd/dealflow-tenant
go run -mod=readonly ./cmd/dealflow-migrate -tenants
```

## 最可能失败的边界

业务 OR 与范围 OR 的分组、同负责人跨租户、附加角色的并集、成员权限版本变化，以及部门树移动后的后代重新解析，是后续仓储接入时的关键回归。

本轮完成成员列表与通用过滤器的 T03 基础覆盖。客户、联系人及客户转移后的关联记录检查按后续计划实现。组织管理的前端页面与浏览器流程本轮未测。已开始的请求使用其解析时的权限快照，下一次解析读取当前成员及部门树。
