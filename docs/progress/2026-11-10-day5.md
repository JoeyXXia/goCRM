## 策略矩阵

| 身份 | 企业菜单 | 本域部门读取 | 本域部门改名 | 平台租户元数据 |
| --- | --- | --- | --- | --- |
| `tenant_admin` | 部门，`canRename=true` | 允许 | 允许 | 拒绝 |
| `sales`、`manager`、`finance` | 部门，`canRename=false` | 允许 | 拒绝 | 拒绝 |
| 未映射角色 | 拒绝 | 拒绝 | 拒绝 | 拒绝 |
| 专用平台账号 | 拒绝 | 拒绝 | 拒绝 | 允许读取 |

角色绑定沿用 `tenant_memberships` 的已验证记录。共享动作矩阵由独立 Casbin 模型在进程内加载，GVA 的策略表保持独立。最容易出错的边界是同一 GVA 角色同时用于两个租户、把菜单返回当作授权，以及平台账号带着同样的 GVA 角色直接访问示例客户接口。

## 实测验收

本地独立 MySQL 8.0.44 上两轮通过。HTTP 用例使用签名 JWT、实际 DealFlow 和 GVA 示例客户路由，以及可回滚的数据库夹具。

| 可观察条件 | 实测结果 |
| --- | --- |
| 同一账号按 A、B 租户分别授权 | A 管理员可读和改名。同一 JWT 在 B 作为销售可读，直接 PATCH 返回 403。企业请求没有对应的 GVA 接口策略。 |
| 平台账号只能读取平台元数据 | 查询 B 的元数据成功。附加企业头返回 400。即使平台账号也有有效企业管理员成员关系，读取部门和企业菜单仍返回 403。 |
| 平台凭据不能读取客户 | 同一个 GVA 角色配置了示例客户 GET 权限。普通账号读到真实夹具，平台凭据访问详情和列表均返回 403，且错误数据为 `null`。 |
| 企业管理员不能借用平台权限 | 企业管理员查询平台租户返回 403。禁用专用平台账号后，原 JWT 查询同一租户也返回 403。 |
| 菜单与直接请求分别校验 | A 的菜单允许改名，B 的菜单隐藏改名，直接请求同样拒绝。禁用 B 成员后旧 JWT 读取菜单和部门均返回 403。相邻 64 位域、未映射客户动作和未映射角色在策略测试中均被拒绝。 |

Day 2 至 Day 4 的迁移、初始化与租户隔离回归也通过。测试连接显式启用 MySQL 时间解析，以读取 GVA 示例客户的时间字段。后端服务及两个 CLI 构建通过。三份 Swagger 文档对新增接口、类型和已有部门接口的定义一致。

## 复现

按 [Day 2 报告](2026-11-08-day2.md) 准备独立的 `dealflow_crm_test` 并设置 `DEALFLOW_TEST_DSN`。进入 `server` 目录运行：

```sh
go test -mod=readonly ./cmd/dealflow-migrate ./cmd/dealflow-tenant ./router/system ./service/tenant -count=2 -v
go build -mod=readonly . ./cmd/dealflow-migrate ./cmd/dealflow-tenant
```

手工复现时，在服务启动前将 `DEALFLOW_PLATFORM_OPERATOR_UUID` 设置为启用的专用 GVA 账号 UUID，使用无 GVA 管理权限的账号。平台账号用 `x-token` 请求 `GET /dealflow/platform/tenants/:id`。用企业管理员的 JWT 重放应得到 403。用企业账号和 `X-Tenant-ID` 请求 `GET /dealflow/menu`，再以销售身份直接发部门 PATCH，应得到 403。

## 范围

- 本轮提供服务端菜单契约。Vue 接入属于 Day 6。未运行浏览器或核验远端 GitHub Actions。
- DealFlow 客户 API 属于 Day 10。客户隔离初版使用已存在的 GVA 示例客户路由验证，同时检查企业策略对尚未映射的客户动作默认拒绝。
