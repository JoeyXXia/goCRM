# DealFlow CRM · Day 4 可信 TenantContext

日期 2026-11-09（Asia/Shanghai）

Day 3 已提供租户、部门和 GVA 账号的成员关系。本轮使用现有部门数据验证请求级租户隔离。客户端通过 `X-Tenant-ID` 选择企业。服务端从已验证的 GVA JWT 取账号 ID，每次查询该账号在所选企业的有效成员关系。

## 三个审查单元

| 改动 | 文件 | 审查重点 |
| --- | --- | --- |
| 可信上下文与数据访问 | [上下文解析](../../server/service/tenant/context.go)、[部门服务与 Repository](../../server/service/tenant/department.go) | 同时校验租户、成员、账号状态。Repository 缺上下文时拒绝，每次读写都限定 `tenant_id` 和部门 ID。 |

| 真实数据库隔离验证 | [Day 4 测试](../../server/cmd/dealflow-migrate/tenant_context_test.go) | 经实际注册的 Gin 路由发送签名 JWT，使用 MySQL 断言越权请求后的记录状态。沿用现有 CI 的迁移测试入口。 |

## 实测验收

本地独立 MySQL 8.0.44 实例运行了 Day 2 至 Day 4 的相关后端测试。两轮均通过，后端和两个 CLI 构建通过。

| 可观察条件 | 实测结果 |
| --- | --- |
| 有效成员可读本租户，租户管理员可改名 | A 查询返回本租户部门。以相同名称连续更新两次成功，数据库中的租户归属与部门编码保持原值。 |
| 每次请求检查当前状态与角色 | 禁用成员、租户或账号，以及软删除账号后，请求返回 403。同一账号作为 B 的销售可读 B 部门，改名返回 403。 |
| 伪造租户选择或请求参数失败 | A 直接选 B 返回 403。缺失或重复租户头、伪造 query/body 字段返回 400。篡改 JWT 返回 401。响应含服务端请求 ID。 |
| 以 A 身份访问 B 的部门 ID 无数据、无变更 | A 保持租户选择为 A，读取和修改 B 的部门均返回 404，错误 `data` 为 `null`。随后按 B 部门 ID 查询，整条记录与初始值一致。 |
| 缺少 TenantContext 时默认拒绝 | 以零值上下文调用读写服务均返回租户权限错误。用例使用空数据库句柄，区分了权限拒绝和数据库不可用。 |

## 复现

按 [Day 2 报告](2026-11-08-day2.md) 准备独立的 `dealflow_crm_test` 并设置 `DEALFLOW_TEST_DSN`。测试会在需要时创建 GVA 用户表、Casbin 表及 Day 2 至 Day 3 迁移表。测试策略仅加入进程内 Casbin，Day 4 数据夹具在事务结束时回滚。进入仓库的 `server` 目录运行。

```sh
go test -mod=readonly ./cmd/dealflow-migrate ./cmd/dealflow-tenant ./router/system -count=2 -v
go build -mod=readonly . ./cmd/dealflow-migrate ./cmd/dealflow-tenant
```

手动复现时，准备两个独立的启用账号和企业，配置 GVA 对应角色的 GET/PATCH 接口权限，再使用各自的 JWT 请求 `/dealflow/departments/:id`。用 A 的 JWT 搭配 B 的 `X-Tenant-ID` 复现 403。保留 A 的租户头并将路径改为 B 的部门 ID，复现 404。

## 边界与未验证项

- 同一账号可以在两个租户具有不同角色。每次请求查当前成员，已通过校验且正在执行的请求不承诺瞬时撤权。本轮未测并发撤权。
- Day 4 以已有部门的查询和改名作为隔离入口，接口权限沿用 GVA。独立 Casbin 域、权限版本和细粒度数据范围分别在 Day 5、Day 8、Day 9 处理。
- 本轮未运行浏览器登录或远端 GitHub Actions。T01 初版覆盖部门详情和改名。
