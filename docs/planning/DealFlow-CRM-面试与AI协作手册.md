## 2. 60 个项目相关面试问题

每题练习顺序：先用自己的话回答，再指向一段代码或测试，最后解释边界。下面是答案骨架，不是背诵稿。前 30 题优先，31–50 题体现业务深度，51–60 题体现完整交付。

### Go 与后端基础：1–10

**1. 从 Python 转 Go，主要变化是什么？**

静态类型、显式错误、接口组合、值/指针语义以及并发模型。举回款 Service 的返回值和错误分类说明；不能只说“Go 更快”。

**2. struct、指针接收者和值接收者怎么选？**

考虑是否修改对象、复制成本和方法集；大结构或有状态组件通常不随意复制。演示 Service/Repository 接口用法，避免把含 mutex 的实例复制。

**3. slice 与 map 的常见坑？**

slice 可能共享底层数组，append 不一定在原数组；map 并发读写需同步；nil map 不能直接写。联系 worker 共享状态或批量分配排序的测试。

**4. interface 应该在哪里定义？**

围绕调用方需要定义小接口，例如 Clock 或通知发送接口；不为了 mock 给每个结构堆一层无意义接口。说明 GVA 已有组织方式与自己的最小扩展。

**5. error 如何传播与映射 HTTP？**

保留原因链，使用 errors.Is/As 等区分未找到、无权、状态冲突、依赖失败。日志保留诊断信息，对外不返回 SQL、token 或私有文件路径。

**6. defer、panic、recover 如何用于事务？**

优先采用经过验证的事务回调并检查返回错误；defer 用于释放资源。panic 不能当业务错误，recover 不能吞掉失败后继续提交。重点检查 tx 句柄，而非只背语法。

**7. context.Context 解决什么问题？**

传递请求期限、取消与请求级元数据，数据库查询关联 context。异步持久任务有独立生命周期，不能直接复用已经结束的 HTTP 请求 context；也不能完全没有超时。

**8. goroutine 比线程轻，为什么不能无限启动？**

仍消耗内存、连接、CPU 和下游资源；后台导出或提醒需要有界并发、取消和等待退出。用 worker 停止后的 goroutine/连接数验证。

**9. channel、mutex 和数据库锁分别管什么？**

channel 协调进程内协作，mutex 保护共享内存，数据库事务锁协调数据库资源。两个 API 实例各有自己的 mutex，不能用它防全系统超收。

**10. `go test -race` 通过意味着什么？**

没有在实际执行到的路径上检测到 Go 内存竞争；不证明不存在其他路径竞争，也不证明数据库金额正确。回款超收要用真实 MySQL 并发与数据库后置断言验证。[Go 官方说明](https://go.dev/doc/articles/race_detector)

### 多租户与权限：11–20

**11. 为什么选共享库共享表？**

单人两个月部署和迁移成本可控，适合练应用隔离；代价是隔离依赖授权、查询、约束和测试的系统性落实。说明独立库的资源隔离优势及迁移/运维代价，不说当前设计是物理隔离。

**12. tenant_id 从哪里来？**

来自已验证身份对应的活动成员关系；客户端只选择当前企业。服务端验证 tenant、membership、状态与版本后形成可信上下文，不能直接信任 header/body。

**13. JWT 里有 tenant 和 role，为什么还查数据库？**

JWT 签名说明令牌来源，不能自动感知成员禁用、角色变更、套餐到期。解释项目的数据库状态检查和已在途请求边界；如果后来加缓存，必须说明陈旧窗口。

**14. Casbin domain 能自动隔离数据库吗？**

不能。domain 让角色/策略在指定租户内生效；对象所在租户和记录可见范围仍需查验，SQL 仍要限定 tenant。[Casbin domains](https://casbin.org/docs/rbac-with-domains/)

**15. 怎么防止平台管理员读取企业合同？**

平台和企业权限上下文、API 分组及策略独立；平台管理租户元数据，不拥有默认 CRM bypass。若未来支持代客操作，需显式授权、时间限制和审计，本期不做。

**16. API 权限、数据范围、套餐权限如何组合？**

身份有效 AND 租户可用 AND 动作允许 AND 模块授权 AND 记录可见，写入还要状态和业务规则通过。前端菜单是呈现层，不是安全依据。

**17. 同一个员工有多个角色，范围怎么计算？**

本项目同一动作的允许范围取并集，再与企业范围取交集；不实现显式 deny。必须按项目实际规则举例，不能让 OR 条件把 tenant 限制绕出去。

**18. 客户转移后，合同/回款权限怎么办？**

以客户为访问根重新计算子单据权限，保留原创建者作为审计事实。财务的组织范围和字段权限单独定义；历史 owner 字段不等于当前访问授权。

**19. 用 GORM Scope 后还有哪些遗漏？**

原生 SQL、关联预加载、JOIN、COUNT、批量更新、文件下载、缓存与后台任务。Scope 是可复用查询逻辑，不会自动替所有数据库操作补隔离。[GORM 文档](https://gorm.io/docs/scopes.html)

**20. 怎样证明隔离而不只是口头保证？**

两企业种子数据，A token 请求 B 对象的列表/详情/写入/关联/聚合/导出/附件矩阵；检查响应与 B 数据库不变，再做同企业跨角色测试。提供测试文件、命令和 CI 结果。

### 数据库与事务：21–30

**21. 为什么子表也要 tenant_id？**

让访问条件、索引、任务定位更直接，配合 `(tenant_id,parent_id)` 复合外键防止跨企业引用。它带来重复字段维护成本，但能把部分错误交给数据库拒绝。

**22. 主键已经全局唯一，复合外键还有价值吗？**

有：只引用全局 ID 只能证明父对象存在，不能证明子记录 tenant 与父对象 tenant 一致。用非法跨租户 INSERT 的集成测试展示差异。

**23. 为什么不用 float 保存金额？**

二进制浮点不能精确表示许多十进制金额。本期金额为 int64 分、API 字符串，校验上限和溢出；分期取整由固定规则处理。多币种和复杂税率不在范围。

**24. GORM 默认写事务能保证回款完整吗？**

单次写入事务不能替代跨多表业务事务。必须把回款、分配、余额、审计、outbox 纳入同一 tx 并传播错误；中途误用全局 DB 会破坏原子性。[GORM 事务](https://gorm.io/docs/transactions.html)

**25. 为什么“先查余额，再写回款”不安全？**

并发请求可能都读到旧余额。需要在事务内锁统一订单/应收资源后校验并更新，或使用正确的条件更新和结果检查；说明多个分配对象的统一锁顺序。

**26. 乐观锁和悲观锁分别用在哪？**

合同草稿编辑用 version 防覆盖；抢合同额度、应收余额用短事务行锁更直观。二者都需要正确条件、错误处理和重试策略，不因用了某一种就自动安全。

**27. 死锁如何处理？**

缩短事务、统一资源顺序、建立合适索引；对可重试数据库错误有限次重试整个事务。业务越权、金额不足不重试，事务中无不可回滚的外部副作用。

**28. 什么地方适合 `SKIP LOCKED`？**

多个 worker 从队列表领取不同任务；它跳过锁定行，返回的不完整视图不适合拿来判断余额、全量金额或合同剩余额度。[MySQL 官方说明](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking-reads.html)

**29. 软删除和唯一编号如何协调？**

本期业务编号删除后不复用，使用 tenant+编号唯一；不把 nullable deleted_at 随意加入唯一键就以为能保证未删除记录唯一。恢复/删除也需授权和状态约束。

**30. 如何设计列表索引和验证效果？**

从真实 WHERE/ORDER BY 与数据分布出发，优先考虑 tenant 和高频条件，再看执行计划、扫描行数、延迟和写入代价；不是每个字段各建一个索引。说明深分页是否需要 keyset。

### 业务正确性：31–40

**31. 合同审批到底在审批什么？**

审批某个冻结版本的金额、条款摘要与附件引用。仅给 contract.status 改成 approved，却允许审批后直接编辑金额，业务语义就不成立。

**32. 两个人同时审批怎么办？**

同一版本、允许状态、指定审批人和 expectedVersion 一起校验，状态更新/决定/审计在一个事务完成。最多一次有效决定，其余返回已处理或状态冲突。

**33. 合同金额 10 万，两张订单各 6 万怎么办？**

订单确认时统一锁合同，核查当前有效占用额度，最多确认一张。只在页面提示或事务外 SUM 不够；取消释放也遵循相同锁规则。

**34. 为什么应收不能只放一个 unpaid 字段？**

分期到期日、部分回款和逾期需要期次；保留应收计划与回款分配才能解释余额。汇总余额可提高查询效率，但必须能从明细复算。

**35. 一笔回款如何分配多个应收期次？**

限定同订单、同客户、同企业、同币种，分配合计等于记账金额，每期不能超过未收；按应收 ID 排序锁定。MVP 不支持跨订单分配和预收余额。

**36. 幂等键和凭证号为什么都要？**

幂等键识别同命令重试，摘要识别同键不同参数；业务凭证号防止换新键重复登记同一业务。幂等响应重放仍需重新授权，不能成为泄漏通道。

**37. 请求返回超时，用户怎么知道记账成功没有？**

用同幂等键重试或查询命令结果，数据库提交的回款与结果引用是判断依据。不能看到超时就自动再生成一张新凭证；测试提交后响应丢失场景。

**38. 冲正为什么不直接删掉原回款？**

新增一次性的补偿记录，保留原始事实、操作者和原因，恢复分配余额；便于审计、对账和解释历史。本期只全额冲正，不伪装成完整会计系统。

**39. 报表的回款率怎么定义？**

同一批选定订单，截至观察时点的净记账回款 / 该批有效应收；期间现金变化另做指标。说明冲正、零分母、取消订单和到期日期，避免分子分母不在同一集合。

**40. 如何测事务回滚？**

在回款分配写入后或审计写入处注入错误，断言回款状态、分配、应收余额、审计、outbox 都未产生部分结果。只测试接口报 500 不能证明数据库回滚。

### SaaS、异步与安全：41–50

**41. 最后一个席位怎么防多人同时占？**

新增和启用成员锁同一个配额资源，再检查和修改；禁用释放、降级超限限制新增。只在前端显示剩余 1 席或无锁 COUNT 都不够。

**42. 过期和禁用有什么区别？**

本项目 expired 保留既有授权用户只读、管理员基础导出；suspended 拒绝企业端访问。都禁止业务写与自动提醒。规则是产品决策，落实到 API/任务/文件，而非只改标签。

**43. 为什么用 outbox？**

避免数据库成功而通知意图丢失：业务与事件同事务保存，再由 worker 执行。它不自动保证通知不会重复，需要业务唯一键、重试与副作用幂等。

**44. 为什么先做 outbox/inbox，再引入 Kafka？**

S1 用真实 MySQL 验证事务、租约、重投与唯一副作用，S5 再接入 Kafka 传输与独立消费者。Kafka 确认不等于外部 MySQL 事务提交，仍需 outbox、inbox 与正确的 offset 提交顺序；当前不再叠加 RabbitMQ。

**45. 任务租约到期，老 worker 又恢复怎么办？**

claim token/version 使旧 worker 无法覆盖新领取状态；副作用也需唯一业务键。不能只校验完成状态，而任由两个 worker 分别生成两条通知。

**46. 通知重试会不会重复催收？**

按 tenant、业务对象、提醒类型、业务日、接收人去重；执行前检查仍逾期和有权；已收清则跳过，历史消息可标已解决。外部邮件若将来加入，需要讨论发送结果不确定性。

**47. 导出任务提交时有权限，下载时没有怎么办？**

创建、执行、下载分别重新授权，私有结果只给当前有权主体。客户转移或成员禁用后拒绝旧文件下载；不能把一个永久公共 URL 当访问控制。

**48. Redis 在项目中负责什么，不负责什么？**

复用 GVA 的必要登录相关用途，按实际实现做限流和非权威缓存；不作为回款、合同额度、席位的唯一事实来源。若 Redis 故障影响登录要如实说明，不宣称所有功能自动降级可用。

**49. Excel 导入有哪些非 CRUD 问题？**

文件/解压/行列限制、模板和字段校验、公式处理、业务权限、关联归属、重复提交、事务大小和错误反馈。本期限定客户模板、500 行整批原子提交。

**50. 审计表是不是不可篡改？**

应用不提供更新入口且关键变更同事务审计；但拥有数据库权限的人仍可能修改表。只有做了额外独立存储/验证机制才可讨论更强防篡改，本项目不夸大保证。

### Vue、运维、性能与项目表达：51–60

**51. Pinia 应该保存什么？**

身份、当前租户、菜单/权限等跨页面状态；表格页局部筛选和表单不必全局化。换企业清理旧缓存、取消请求或用上下文版本丢弃晚到响应。

**52. Vue 表单验证通过就能保存吗？**

不能，后端重新做格式、权限、状态、金额和关联校验。页面应区分输入错误、权限拒绝和并发冲突，避免失败后仍显示成功状态。

**53. 前端什么地方最值得测试？**

金额解析/展示、状态动作、权限变化、租户切换的旧请求、回款错误反馈；E2E 覆盖关键跨角色闭环。单纯重复实现细节的组件快照价值有限。

**54. p95 与 QPS 应该怎么一起看？**

说明固定硬件、数据量、并发/速率和持续时间；吞吐提升但尾延迟或错误恶化未必有价值。预期业务冲突与系统失败分开统计，性能测试后还要查业务不变量。

**55. 接口变慢怎样排查？**

通过 requestID 和指标定位应用、DB 池等待、锁等待、SQL、外部依赖或 CPU；执行计划/pprof 验证假设，改一个热点再同条件复测，而非先加缓存。

**56. 为什么 readiness 不等于进程活着？**

进程可运行但关键数据库不可用；readiness 判断是否可接流量，liveness 判断是否需要重启。避免依赖瞬时波动导致无意义重启风暴。

**57. 镜像回滚能自动回滚数据库吗？**

不能。迁移需考虑前后版本兼容，破坏性结构变更有专门恢复方案；备份必须经过恢复验证，不能只说“有定时备份”。

**58. 项目用了 GVA，哪些是你做的？**

明确登录、布局等上游能力；自己的租户上下文/数据范围、版本审批、回款事务、任务与测试用 commit/ADR 证明。不把生成器产出的通用 CRUD 包装成全部原创。

**59. AI 写了很多代码，你的能力体现在哪里？**

你定义业务规则和边界、选择方案、检查 diff、设计独立验收、复现并修复故障，能现场改代码。拿一个 AI 初稿有漏洞而你通过测试纠正的真实例子，不能编故事。

**60. 如果再给一个月，先做什么？**

根据已知瓶颈和目标岗位选择：扩展审批配置、真实对象存储、权限失效多实例机制，或更深性能诊断。先说明需求和验证收益，不机械堆微服务/K8s/AI。

## 3. 每天怎样用 AI，才不会只剩提交记录

你负责：需求、权限边界、金额口径、不可违反的规则、验收和最终签收。AI 负责协助查源码、提出方案、写局部实现、生成测试候选、做 diff 审查和整理文档。

每个工作块尽量 30–60 分钟，结束时有可审查改动。先看仓库约定和已有代码，再提最小方案；不要一次让 AI 重写整套 GVA。核心事务你必须逐行读，亲自跑负例。

### 每日开工提示词


## 4. 提交、Issue 与 PR 的做法

一个 Issue 表达一个可验收问题，如“并发回款不得超过应收余额”。提交围绕可审查变化，不按文件机械切碎。

合适的一个工作日：

```text
feat: post receipts within a single transaction
test: reject concurrent allocations above outstanding balance
docs: explain receipt lock order and retry behavior
```

低价值做法：空提交、重复改文案、倒改日期、把一个无法运行的函数拆成十次提交，或者把 AI 生成测试但未执行写成“测试通过”。

个人仓库也可以用短分支 + PR 汇总一项业务，让读者看到问题、实现与验证。如果为了展示逐步历史，选择保留有意义的小提交的合并方式；是否 squash 依据实际团队习惯。每周打版本标签，不每天都造 Release。

PR 描述模板：

```text
问题：两个财务可能同时读取旧余额，导致重复分配。
行为：记账按订单和应收顺序锁定，额度不足返回业务冲突；重复命令返回原结果。
验证：写明实际运行的集成测试/故障注入和结果链接。
边界：目前一张回款仅对应一个订单，只支持全额冲正。
```

## 6. 基础学习与完成标准

每日独立学习约 30 分钟，交替练 Go 与通用基础：HTTP/TLS、cookie/token、SQL JOIN/索引/隔离、进程线程、内存和并发、常见数据结构。每周两道小算法题即可作为补充；不以刷题挤占业务验证。

建议独立手写的五个小练习：金额字符串转分、部门后代集合、带租户和范围的分页查询、幂等记账事务伪代码、可取消的有界 worker。可用项目测试检验，不要求重新造复杂框架。

- 每个核心亮点都有实现、失败用例和实际验证结果。
